# CheckStock: архитектура и логика приложения

Источник правды по тому, как устроено приложение. Код должен соответствовать этому файлу; если что-то меняется, меняется и файл.

## 1. Задача

Тестовое задание «Где сейчас товар?»: веб-прототип для менеджера. Один артикул может лежать на нескольких складах фулфилмента (ФФ), быть зарезервированным под FBS или ехать на склад маркетплейса по FBO. Менеджер сразу видит, где товар, сколько доступно и что уже отправлено.

Стек зафиксирован заданием: **Python, FastAPI, PostgreSQL**. Срок: 1 рабочий день. ИИ использовать можно, но автор должен объяснить каждое решение.

Как оценивают:
- 40%: учёт остатков после прихода, резерва, перемещения, отправки, приёмки;
- 25%: нехватка на выбранном ФФ, удаление ФФ с остатком, повторное подтверждение;
- 15%: понятность интерфейса и кода, простота запуска и проверки;
- 20%: ход мысли и объяснение решений в видео.

Тестовые данные: один магазин, два ФФ.

| Артикул | Товар | Север | Юг |
|---|---|---|---|
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

## 2. Главная идея

Единицы товара **не создаются и не исчезают, а только переходят из одного места в другое**. Остаток нигде не хранится числом: он считается как «всё, что пришло в место, минус всё, что ушло из него» по **журналу движений**. Аналогия: банковская выписка. Если ошибся, не правишь баланс, а добавляешь новую операцию.

Следствия:
- история операций (требование задания) получается сама собой;
- сходимость проверяется простой сверкой (раздел 11);
- «в пути» это не особая колонка, а баланс виртуального места.

## 3. Места (таблица `locations`)

| name | kind | Смысл |
|---|---|---|
| Север, Юг, ... | `ff` | реальные склады ФФ; можно добавлять, переименовывать, архивировать |
| EXTERNAL | `external` | откуда товар приходит впервые |
| TRANSIT_TRANSFER | `transit_transfer` | в пути между ФФ |
| TRANSIT_FBO | `transit_fbo` | в пути на склад маркетплейса |
| TRANSIT_CLIENT | `transit_client` | в пути к клиенту (FBS) |
| MARKETPLACE | `marketplace` | принято маркетплейсом (FBO) |

Каждое виртуальное место существует ровно одно (уникальный индекс по `kind` для всех, кроме `ff`). Создаются seed-ом.

## 4. Таблицы

Схема в `app/schema.sql` (`CREATE ... IF NOT EXISTS`, применяется при старте).

- `products(id, sku UNIQUE, name)`
- `locations(id, kind, name UNIQUE, is_archived)`
- `movements(id, product_id, qty > 0, from_location_id, to_location_id, op_type, op_id, created_at)`: **только дописывается**; `from <> to`. `op_id` это id операции-источника (перемещения, резерва, FBO-отправки), для прихода NULL.
- `reservations(id, product_id, location_id, qty, status: active | shipped | cancelled, created_at)`
- `transfers(id, product_id, qty, from_location_id, to_location_id, status: created | sent | received, created_at)`
- `fbo_shipments(id, product_id, qty, from_location_id, status: created | sent | accepted, created_at)`

Seed (`init_db()` в `app/db.py`): выполняется в одной транзакции под `LOCK TABLE products` и только если таблица `products` пуста. Повторный запуск ничего не дублирует.

## 5. Как считаются показатели

Для товара P и места L:

- **баланс(P, L)** = Σ qty движений «в L» − Σ qty движений «из L»
- **на складе** = баланс ФФ
- **резерв** = Σ qty резервов со статусом `active` на этом ФФ
- **доступно** = на складе − резерв (всегда ≥ 0)
- **в пути между ФФ** = баланс `TRANSIT_TRANSFER`
- **в пути на склад МП (FBO)** = баланс `TRANSIT_FBO`
- **в пути к клиенту (FBS)** = баланс `TRANSIT_CLIENT`
- **у маркетплейса** = баланс `MARKETPLACE`

Реализация: `BALANCES_CTE` в `app/stock.py` (UNION ALL «пришло» и «ушло», затем GROUP BY).

## 6. Операции и движения

| Операция | op_type | Движение | Предусловия |
|---|---|---|---|
| Приход | `receipt` | EXTERNAL → ФФ | ФФ не в архиве |
| Отправка перемещения | `transfer_send` | ФФ-источник → TRANSIT_TRANSFER | статус `created`; доступно ≥ qty; получатель не в архиве |
| Приёмка перемещения | `transfer_receive` | TRANSIT_TRANSFER → ФФ-получатель | статус `sent`; получатель не в архиве |
| Резерв FBS | нет движения | блокирует часть «доступно» | ФФ не в архиве; доступно ≥ qty |
| Отправка FBS | `fbs_ship` | ФФ → TRANSIT_CLIENT | резерв `active` |
| Отмена FBS | нет движения | резерв закрывается | резерв `active` |
| Отправка FBO | `fbo_send` | ФФ → TRANSIT_FBO | статус `created`; доступно ≥ qty |
| Приёмка FBO | `fbo_accept` | TRANSIT_FBO → MARKETPLACE | статус `sent` |

Резерв FBS **не двигает товар**: на складе остаётся прежнее число, уменьшается только «доступно». Товар физически уходит при отправке заказа.

## 7. Статусные автоматы

```
transfers:    created --send--> sent --receive--> received
reservations: active --ship--> shipped
              active --cancel--> cancelled
fbo:          created --send--> sent --accept--> accepted
```

Каждый переход разрешён только из одного предыдущего статуса.

## 8. Идемпотентность и конкурентность

Задание: «повторное подтверждение не списывает товар дважды».

1. Переход проверяется **под блокировкой строки** операции: `SELECT ... FOR UPDATE OF <таблица операции>`. Параллельный повтор ждёт и видит уже новый статус.
2. **Повтор уже выполненного перехода** (send для `sent`/`received`, receive для `received`, ship для `shipped`, cancel для `cancelled`, accept для `accepted`) возвращает 200 с тем же объектом и `"replayed": true`. Движений не создаётся.
3. **Недопустимый переход** (receive до send, ship после cancel, cancel после ship) возвращает 409 с понятным текстом.
4. Проверка «доступно ≥ qty» делается только под `lock_product(conn, product_id)` (`SELECT 1 FROM products WHERE id = ... FOR UPDATE`). Так два одновременных списания не продадут один и тот же остаток.
5. **Порядок блокировок всегда один**: сначала строка операции, потом строка товара. Это исключает взаимные блокировки (deadlock).
6. Транзакция = один `with connect() as conn:` на запрос; исключение откатывает всё.

## 9. Нехватка

Если на выбранном ФФ «доступно» меньше нужного, товар **молча с другого ФФ не берётся**. Ответ 409:

```json
{"detail": {
  "error": "insufficient_stock",
  "message": "На складе «Север» доступно 0, нужно 3. Хватает на: Юг. Оформите перемещение с него.",
  "needed": 3,
  "available_here": 0,
  "available_elsewhere": [{"warehouse_id": 7, "name": "Юг", "available": 4}]
}}
```

Подсказка бывает трёх видов: есть ФФ, где хватает; есть ФФ, где товар есть, но по отдельности мало; товара нет нигде. Состояние базы при этом не меняется. Общая функция формирования ответа живёт в `app/stock.py` и используется перемещениями, FBS и FBO.

## 10. Склады: переименование и удаление

- Добавить ФФ: `name` уникально, не пустое после `strip`, не совпадает с именами виртуальных мест.
- Переименовать: меняется только `locations.name`. История ссылается на `id`, поэтому остаётся целой.
- **Удалить = архивировать** (`is_archived = true`). Физически строки не удаляются, иначе пропадёт история. Остатки и движения сохраняются, склад виден в `/stock` с `archived: true`.
- Архивный ФФ: **входящее запрещено** (приход, создание/отправка/приёмка перемещения на него, новые резервы, 409); **исходящее разрешено** (перемещение с него, отправка уже зарезервированных FBS, FBO), чтобы остаток можно было вывезти.
- Архивирование отклоняется (409), если есть перемещения `sent` в этот склад: товару в пути некуда приехать.
- Гонка «архивируем / одновременно кладём на склад» закрывается так: входящие операции читают `is_archived` под `FOR SHARE` строки склада, архивирование берёт `FOR UPDATE`.
- Повторное удаление уже архивного склада возвращает 200 и `replayed: true`.
- Возврат из архива: `POST /warehouses/{id}/unarchive`, идемпотентно; после разархивирования входящие операции снова разрешены.

## 11. Инвариант (главная проверка)

Для каждого товара: **Σ балансов всех мест, кроме EXTERNAL, = Σ приходов (`receipt`)**. Иначе где-то баг. Тесты проверяют инвариант после каждой операции.

Также: «на складе» ≥ «резерв» на любом ФФ, а «доступно» ≥ 0.

## 12. API

Все перечисленные эндпоинты реализованы. Ошибки: 404 (не найдено), 409 (конфликт состояния, нехватка, архив), 422 (неверный ввод, `qty ≤ 0`).

## 14. Решения и компромиссы

- **psycopg + чистый SQL, без ORM.** Для учёта важны точные транзакции и блокировки строк, в SQL они видны прямо в коде.
- **Журнал вместо чисел.** Нельзя «забыть обновить остаток», история бесплатна.
- **Виртуальные места.** Любая единица товара всегда в ровно одном месте, проверка сходимости становится арифметикой.
- **Мягкое удаление ФФ.** История и остатки не теряются.
- **Jinja-шаблоны и один JS-файл без фреймворка.** Задание про учёт, а не про фронтенд; запуск не требует сборки.
- **Сознательно не делаем:** доставку FBS клиенту (товар остаётся «в пути к клиенту»), авторизацию, пагинацию, систему миграций (схема через `IF NOT EXISTS`), несколько магазинов (в задании один).
