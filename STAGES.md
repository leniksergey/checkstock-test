# CheckStock: этапы

Правило: **один этап = код → запуск → проверка «Готово когда» → коммит `Этап N: ...`**. К следующему этапу не переходим, пока условие не выполнено. Логика и контракты API описаны в `ARCHITECTURE.md`.

Оценка времени на оставшиеся этапы: ~5,5 часа.

## Сделано

### Этап 0. Каркас ✅
`docker-compose.yml` (Postgres 16 + приложение, приложение стартует после healthcheck базы), `Dockerfile`, FastAPI с `/health` (делает `SELECT 1`), `db.py`.
**Готово когда:** `docker compose up --build` → `/health` отвечает `{"status":"ok"}` с чистого клона.

### Этап 1. Модель данных и seed ✅
`app/schema.sql` (6 таблиц), `init_db()` в `app/db.py`: места, товары, тестовый приход как 4 движения из EXTERNAL. Seed в одной транзакции и только на пустой базе.
**Готово когда:** после запуска остатки 10 / 6 / 5 / 4, повторный запуск ничего не дублирует.

### Этап 2. Приход и расчёт остатков ✅
`app/stock.py` (`BALANCES_CTE`, `get_stock`, `on_hand`), `GET /stock`, `POST /receipts`.
**Готово когда:** `/stock` показывает цифры из задания, приход меняет остаток.

### Этап 3. Перемещения между ФФ 🟡 код готов, идёт проверка
`app/transfers.py` (роутер `/transfers`), в `app/stock.py` добавлены `lock_product`, `available`, `other_stock`. Статусы `created → sent → received`, `replayed`, подсказка при нехватке, блокировка `FOR UPDATE`.
**Готово когда:** Север → Юг 4 шт.: после send «между ФФ» = 4, Юг не изменился; после receive Юг +4; повторный send/receive ничего не меняет; нехватка на Севере при наличии товара на Юге даёт 409 с подсказкой.
**Проверить наличие:** если `app/transfers.py` в репозитории нет, реализовать этап по `ARCHITECTURE.md` (разделы 6–9).

## Осталось

### Этап 4. FBS: резерв, отправка, отмена (~1 ч)
Файлы: новый `app/fbs.py` (роутер `/fbs`), подключить в `main.py`.
1. В `app/stock.py` вынести формирование ответа о нехватке из `transfers.py` в общую функцию (например, `insufficient_stock(conn, product_id, location_id, location_name, qty, free)`, возвращает `HTTPException(409, {...})`). `transfers.py` перевести на неё, поведение не менять.
2. `POST /fbs/orders {sku, warehouse_id, qty}`: под `lock_product` проверить `available ≥ qty`, иначе 409 с подсказкой; ФФ в архиве → 409. Создать резерв `active`. Движений нет.
3. `POST /fbs/orders/{id}/ship`: блокировка строки резерва `FOR UPDATE`; `active` → движение ФФ → `TRANSIT_CLIENT` (`op_type='fbs_ship'`, `op_id` = id резерва), статус `shipped`; `shipped` → `replayed: true`; `cancelled` → 409.
4. `POST /fbs/orders/{id}/cancel`: `active` → `cancelled`, движений нет; `cancelled` → `replayed`; `shipped` → 409.
5. `GET /fbs/orders`: список резервов с названием склада.

**Готово когда** (SKU-101, Север = 10):
- резерв 3: на складе 10, резерв 3, доступно 7;
- перемещение 8 шт. с Севера на отправке даёт 409 (доступно 7), товар не тронут;
- ship: на складе 7, резерв 0, «к клиенту» = 3; повторный ship ничего не меняет;
- отмена другого резерва возвращает «доступно», «на складе» не меняется; cancel после ship даёт 409.

Для README/видео: резерв блокирует «доступно», но не двигает товар; товар уходит только при отправке; отмена возвращает доступность без движений.

### Этап 5. FBO (~30 мин)
Файлы: новый `app/fbo.py` (роутер `/fbo`); `get_stock` в `app/stock.py`.
1. `POST /fbo {sku, warehouse_id, qty}` создаёт отправку `created`.
2. `POST /fbo/{id}/send`: `created` → под `lock_product` проверить `available ≥ qty` (иначе 409 с подсказкой), движение ФФ → `TRANSIT_FBO` (`fbo_send`), статус `sent`; повтор → `replayed`.
3. `POST /fbo/{id}/accept`: `sent` → движение `TRANSIT_FBO` → `MARKETPLACE` (`fbo_accept`), статус `accepted`; `accepted` → `replayed`; `created` → 409.
4. `GET /fbo`: список.
5. В `GET /stock` на каждый товар добавить поле `at_marketplace` (баланс `MARKETPLACE`).

**Готово когда:** после send товар ушёл с ФФ и числится в «в пути на склад МП»; после accept он в `at_marketplace`, «в пути» = 0; повторный send/accept не дублирует; сумма по всем местам не меняется.

### Этап 6. Склады и «где числится товар» (~45 мин)
Файлы: новый `app/warehouses.py` (роутер `/warehouses`); правки в `transfers.py`, `fbs.py`, `main.py` (приход).
1. `GET /warehouses`: ФФ с `id`, `name`, `archived`, суммарным остатком.
2. `POST /warehouses {name}`: `strip`, не пустое, уникальное, не совпадает с именами виртуальных мест → иначе 409/422.
3. `PATCH /warehouses/{id} {name}`: меняет только `name`; то же правило уникальности.
4. `DELETE /warehouses/{id}`: **архивирование** (`is_archived = true`), остатки и история не трогаются; уже архивный → 200 + `replayed`; есть перемещения `sent` в этот склад → 409. Строка склада берётся `FOR UPDATE`.
5. Правила архивного ФФ из `ARCHITECTURE.md`, раздел 10: входящее запрещено везде (приход, создание/отправка/приёмка перемещения на него, новый резерв), исходящее разрешено. Проверку `is_archived` во входящих операциях делать под `FOR SHARE` строки склада. В `transfers.send` добавить проверку получателя.
6. `GET /stock/{sku}/locations`: все места, где у товара ненулевое количество (ФФ включая архивные, «в пути», у МП), с количеством и резервом.

**Готово когда:** ФФ с остатком архивируется, остатки и история на месте, склад виден в `/stock` с `archived: true` и в `/stock/{sku}/locations`; приход и перемещение на него дают 409; перемещение с него разрешено; переименование не ломает историю.

### Этап 7. История и экран (~1 ч)
Файлы: новый `app/history.py`, `app/static/index.html`, раздача в `main.py`.
1. `GET /history?sku=&warehouse_id=&limit=200`: движения с названиями мест, от новых к старым: `created_at`, `sku`, `qty`, `from`, `to`, `op_type`.
2. `GET /` отдаёт `app/static/index.html`. Один файл, vanilla JS + `fetch`, **без фреймворков и внешних CDN**.
3. Экран: таблица остатков (по SKU × ФФ: на складе / резерв / доступно; отдельно три «в пути» и «у МП»; архивные склады помечены); формы прихода, перемещения, FBS-заказа, FBO-отправки; списки операций с кнопками send/receive/ship/cancel/accept; управление складами (добавить, переименовать, архивировать); история.
4. Ошибки сервера показываются на экране; для нехватки выводится `message`. Кнопки блокируются на время запроса.

**Готово когда:** весь сценарий (приход → резерв → перемещение → отправка → приёмка, нехватка, архивирование) проходится мышкой, без curl.

### Этап 8. Тесты (~45 мин)
Файлы: `tests/conftest.py`, `tests/test_*.py`, правка `Dockerfile` (`COPY tests tests`).
- Тесты идут в **отдельной БД** `checkstock_test`: `conftest.py` выставляет `DATABASE_URL` **до импорта** `app`, создаёт БД, перед каждым тестом пересоздаёт схему и seed.
- Хелпер `assert_invariant()` (`ARCHITECTURE.md`, раздел 11) вызывается после каждой операции.
- Запуск: `docker compose run --rm app pytest -q`.

Сценарии:
1. приход → остатки;
2. резерв → доступно уменьшилось, на складе то же;
3. перемещение send / receive;
4. отправка FBS;
5. FBO send / accept;
6. **нехватка** на одном ФФ при достаточном общем остатке → 409, состояние не изменилось;
7. **удаление ФФ с остатком** → остатки и история на месте, входящее запрещено;
8. **повторные** receive / ship / accept / cancel → `replayed`, без двойного списания;
9. параллельные запросы: 8 потоков на один `receive` → ровно одно движение; два перемещения на весь остаток → одно проходит, второе 409.

**Готово когда:** все тесты зелёные.
