# CheckStock

Прототип системы складского учёта («Где сейчас товар?») для менеджера склада, работающего по схемам FBS и FBO. Приложение позволяет в реальном времени отслеживать физические остатки, резервы, товары в пути и полный журнал движений.

## Основные возможности

* **Остатки по складам ФФ:** сколько товара физически на складе, в резерве FBS и доступно для операций.
* **Товары в пути:** перемещения между складами ФФ, поставки на склад маркетплейса (FBO) и заказы в доставке клиенту (FBS).
* **Учёт на маркетплейсе:** количество товара, уже принятого на складе МП.
* **Журнал движений:** полная история операций — когда, откуда, куда и сколько единиц перемещено.

## Стек технологий

* **Backend:** Python 3.12, FastAPI, PostgreSQL 16
* **База данных:** `psycopg 3` (чистый SQL, без ORM)
* **Frontend:** Jinja2-шаблоны, Vanilla JS (`app.js`, без фреймворков), Tabler CSS (локально, без CDN)
* **Инфраструктура:** Docker Compose

При первом запуске `init_db()` автоматически создаёт схему БД и засевает тестовые данные:

* **Склады ФФ:** Север, Юг
* **Товары:** `SKU-101` (Органайзер), `SKU-102` (Контейнер), `SKU-103` (Корзина)

## Тестирование

Запуск автотестов выполняется в изолированной базе `checkstock_test`:

```bash
docker compose run --rm app pytest -q
```

Набор из 10 интеграционных тестов проверяет:

* оприходование товара и пересчёт остатков;
* резервирование под FBS (уменьшает «доступно», не изменяя «на складе»);
* перемещение между складами (`send` / `receive`);
* отгрузку заказов FBS (`ship`) и поставки FBO (`send` / `accept`);
* обработку нехватки товара (`409 Conflict` с подсказкой по остаткам на других складах);
* архивирование склада с остатком;
* идемпотентность подтверждений (повторные `receive`, `ship`, `accept`, `cancel` не списывают товар дважды);
* соблюдение инварианта: сумма балансов всех локаций (кроме `EXTERNAL`) всегда равна сумме приходов.

## Ключевые архитектурные решения

### 1. Журнал движений вместо хранения остатка числом

Текущий остаток не хранится в отдельной колонке — он вычисляется агрегацией таблицы `movements`:

$$\text{Баланс}(\text{место}) = \sum \text{Приход} - \sum \text{Расход}$$

* Таблица `movements` работает в режиме `INSERT-only` (без `UPDATE` и `DELETE`). Ошибки исправляются компенсирующей операцией, как в банковской выписке.
* История движений формируется автоматически, а сходимость данных проверяется арифметическим инвариантом.

### 2. Виртуальные места (локации)

Каждая единица товара в любой момент времени находится ровно в одной локации:

* `EXTERNAL` — внешний источник (поставщики);
* `TRANSIT_TRANSFER` — в пути между складами ФФ;
* `TRANSIT_FBO` — в пути на склад маркетплейса;
* `TRANSIT_CLIENT` — в пути к клиенту (FBS);
* `MARKETPLACE` — принято маркетплейсом.

Благодаря этому статус «в пути» рассчитывается тем же SQL-запросом, что и баланс физического склада.

### 3. Статусные автоматы и идемпотентность

Каждый переход статуса разрешён строго из одного предыдущего состояния:

* `transfers`: `created → sent → received`
* `reservations`: `active → shipped | cancelled`
* `fbo`: `created → sent → accepted`

Переход проверяется под блокировкой `SELECT ... FOR UPDATE` строки операции. Повторное подтверждение уже выполненного шага возвращает `200 OK` с `"replayed": true` без создания новых движений.

### 4. Блокировки и защита от Deadlock

Перед проверкой условия `available >= qty` вызывается `lock_product(conn, product_id)` (`SELECT ... FOR UPDATE` на строке товара), что исключает гонку при параллельных списаниях. Во всех транзакциях соблюдается единый порядок захвата блокировок: сначала строка операции, затем строка товара.

### 5. Нехватка остатков с подсказкой

При попытке списать со склада больше доступного количества система не забирает товар с других складов автоматически, а возвращает ошибку `409 Conflict` со списком складов, где товар есть в наличии:

```json
{
  "error": "insufficient_stock",
  "message": "На складе «Север» доступно 0, нужно 3. Хватает на: Юг. Оформите перемещение с него.",
  "needed": 3,
  "available_here": 0,
  "available_elsewhere": [
    {"warehouse_id": 7, "name": "Юг", "available": 4}
  ]
}
```

### 6. Мягкое удаление складов (Soft Delete)

Запрос `DELETE /warehouses/{id}` переводит склад в архив (`is_archived = true`), сохраняя историю и текущие остатки:

* входящие операции на архивный склад запрещены (`409 Conflict`);
* исходящие операции (вывоз остатков на другой ФФ, отгрузка ранее зарезервированных FBS/FBO) разрешены;
* возврат из архива выполняется идемпотентным запросом `POST /warehouses/{id}/unarchive`.

```text
├── templates/

│   └── index.html   # Интерфейс из трёх секций: остатки, склады, история
└── static/
    ├── js/app.js    # Логика фронтенда (fetch, селекты, локализация)
    └── assets/tabler/css/tabler.min.css
tests/               # Интеграционные тесты (pytest, изолированная БД, 10 сценариев)
docker-compose.yml
Dockerfile
requirements.txt
```

## Осознанные ограничения MVP

В рамках тестового прототипа за скобки вынесены инфраструктурные задачи, не относящиеся к ядру складского учёта:

* финальный статус доставки FBS клиенту (товар фиксируется в статусе `TRANSIT_CLIENT`);
* авторизация пользователей и пагинация таблиц;
* версионирование миграций БД (используется идемпотентный `schema.sql`);
* мультиаккаунтность (учёт ведётся в рамках одного магазина).
